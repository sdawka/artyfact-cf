## C.0 Foundations
react-router 7 data mode; routes `/` (Home), `/s/:systemId/r/:rev/{overview,map,journeys,theory,code,work,review,evaluations,changelog,compare,phenome}`, each also under `…/things/:thingId/` (`/s/:systemId` opens the sole Thing's workspace when the System has one Thing, else head's overview; `…/history` redirects to `…/changelog` and `…/work?panel=promote` to `…/review?panel=promote`, both keeping every param and the hash); global params `focus`, `layer`, `candidates` preserved by nav links; view-specific `journey`, `step`, `evolution`, `realization`, `panel`, `evaluation`, `commit`, `repo`, `path`, `from`, `to`, `level`, `deployment`, `build`. ## C.6 Work
New work follows the [lifecycle](lifecycle.md): Genome-only Evolutions and separate Realization plans pinned to accepted Genome revisions. Work exposes Tasks, scope interference, dependencies, attempts and one combined implementation review. Older Evolution-owned attempts remain readable as legacy history. `/start` previews native ontology packages and preserves invalid conversion output for correction before exact-hash acceptance.

EvolutionBoard columns by state; EvolutionCard scope chips, "≈ overlap" when any of its candidates conflicts and "N await review" (attention) when candidates or amendments wait; RealizationRow (agent, role, local/hosted, status, fork + short sha, last checkpoint or "unknown", changed subjects, ConflictChips typed, inline "Review" toggle, "Open in Review"); StartWorkPanel → PacketViewer (markdown, copy, CLI line, token countdown); inline CandidateReview tabs Semantic delta / Files / Evaluations / Amendment, "select for composition" → `?candidates=`. "Promote in Review" is a link to Review's desk (`/review?evolution=E&panel=promote`, keeping `?candidates=`); `/work?panel=promote` redirects there. The card's "N await review" counts candidates, stale candidates and amendments, not the promotion row.

**Plan** (`views/work/plan/`; `?panel=plan` for the draft, `?plan=` and `?task=` for the detail). The list and detail read `src/api/lifecycle.ts`, polled (plans emit no SSE events); counts use the live `GET /api/systems/:id`, never the cached systems list. Writes need the admin token and say so.
- *Draft flow.* The draft panel picks accepted Genome Evolutions, optional node ids and a hint, and "Draft tasks" posts to the draft route (backend.md B.9), which saves nothing. It shows provenance, problems and the drafted waves. Rename, merge (same binding only, dependents repoint), split by write nodes (dependents wait on both halves) and remove edit the draft in the browser; the waves line then says they are recomputed on create. `draftErrors` catches what create would refuse (duplicate ids, unknown dependencies, cycles, no title, no write node). "Create plan" posts `{...draft.request, title, tasks}` unchanged to create. There is no plan PUT, so a created plan is edited by drafting again.
- *Wave board.* One region per `analysis.waves` entry, "Wave n · k tasks" (1-based). `TaskCard`: status chip (`pending ○ claimed ◔ working ◑ submitted ◕ selected ◉ completed ●`; blocked is a pending task with a dependency that has no selected candidate, shown with "waits on …"), up to four write-node chips, binding and footprint line, depends-on, conflict chips (dependency, source, ontology, unknown; each names the other task, none danger-toned) and "awaits an agent".
- *Commands.* Each wave lists, per task an agent can take now, the claim line and an agent subshell, with Copy and Hide each: `npx artyfact task claim <plan> <task> --system <sys> --dir ./work/<task>` and `( cd ./work/<task> && env -u ARTYFACT_ADMIN_TOKEN claude -p '<prompt>' )`. A lapsed lease shows `resume`; a task a conflicting live attempt blocks, or whose id fails the CLI's id rule, shows its reason instead. Every id is shell-quoted. "Copy all" copies the still-shown claims first, from the shell's own directory, then every agent subshell in the background and one `wait`, so a wave's agents run side by side. It is disabled once everything is hidden. The SPA never handles credentials: the admin token stays in the person's shell and the line that starts the agent unsets it.
- *Task detail.* Why the task is in its wave, its command, write and read nodes, the footprint (globs, files written, unmatched files, read scope), steps, checks with `VerdictBadge`, depends-on, attempts, and the select form for a submitted candidate. "Integrate selected Task results" is disabled with its reason until every task is selected; once integrated, `PlanReview` shows the combined implementation review and per-binding changes before promote. A 409 `replan-required` says to create a new plan.
- Fixture data shows the list read-only with every write disabled.

## C.6a Describe a change by intent
`?panel=intent` on Work (`views/work/intent/`): a message, optionally anchored on a node, becomes a Proposal (routed path, the agreement tree over its ops, questions with inline replies). The proposal already links to a durable Genome Evolution. Accepting commits the agreed Genome change at once; implementation starts separately in a Realization plan. While the panel is open it replaces the Evolution board and detail; its head shows the anchor as a node chip with "Clear anchor", and "Back to board" closes it and keeps the other params. "Describe a change" is the one label at every entry (Work header, Home card, Inspector, Code file pane) and the Work header's one primary action; "+ Evolution" is a secondary text button. The UI is driven by template view hints, not by node kind (`docs/design/ontology.md`).

**Agreement tree** (`intent/agreement/`, `AgreementTree`): `Proposal.plan` as rows rooted at Things, each with the kind glyph, title, counts ("3 add · 2 update · 1 remove" over its subtree), the rollup word (agreed, rejected, deferred, mixed, undecided) and Agree / Reject / Defer toggles (`aria-pressed`, named "Agree <title>"). An open node shows its own ops' diffs; no per-op checkboxes. Children inherit a node's decision; deciding a node clears its descendants' decisions, and a child decided afterwards overrides it (the parent shows "mixed"). Backspace or a second click clears a node's own decision. A node with an `error` problem cannot be agreed; an agreed op that needs a rejected or deferred one is left out and its node says "needs <title>". Decisions persist through `PUT …/intents/:pid/decisions` (optimistic, rolled back on refusal; ontology.md §5); a proposal without a stored plan gets one from the model index (`planFromOps`) and keeps decisions in the view. Rule styles, never green: agree solid apricot, reject dashed with secondary text, defer dotted with a "deferred" chip, mixed at half strength. All open when at most five nodes own ops, else only the Things. Keyboard: one tab stop with roving focus; ↑↓ move, → opens or enters, ← closes or goes to the parent, Home/End, Enter/Space open and close, `a` `r` `d` decide, Backspace clears; a hint line under the tree says so. Variant `genome` (import and amendment review) has no Defer. Fixture: every decision disabled, the tree still navigable.

**Accept agreed** sends the agreed, unblocked ops; it is disabled with a reason while any node is undecided or nothing is agreed. The summary reads "11 of 14 changes agreed · 1 deferred · 2 rejected". It commits exactly the agreed changes to the Genome. With deferred nodes the platform moves their ops to a new proposal with its own Evolution and the panel stays open: "Accepted 11 changes into <Evolution> and committed them to the Genome. 3 deferred changes wait in a new proposal." with "Continue with deferred" (opens that proposal) and "Open the candidate".

## C.6b Review
`/review` (`views/review/`), the operator's inbox and promotion desk, two panes. Left, the decision queue ("Waiting on you N"), grouped by Evolution, one row per pending decision: `import` (the System's import review is pending, `SystemSummary.importReview`), `candidate` (submitted/evaluated, not promoted or rejected), `stale` (its base is behind head, dashed attention), `amendment` (Genome realization `awaiting-admin`), `promotion` (an Evolution with an evaluated candidate on the current head). A row shows the kind word, agent and role, candidate id ("selected for composition" when it is in `?candidates=`), ConflictChips (one per kind, with the count) and "base = head" (neutral), "behind by N" or "behind head" when the distance is unknown (attention); a promotion row reads "ready to promote". An import row reads "Import · 121 nodes", "awaits an admin" and the Genome commit, with an attention rule on its left; it is its own group, "Import", before every Evolution, because new Evolutions, realizations, intents and lifecycle work are refused (409 `import-unreviewed`) until it is accepted. The queue takes the summary's pending status unless the review itself (`GET …/import-review`) says accepted. Within a group: amendments, then candidates, then the promotion row. Right, the selected row: the import review (`?panel=import`, `GenomeReview`: the containment tree with Agree and Reject per node, readiness findings, unmapped paths with their total, an interpretation field), CandidateReview (`?evolution=&realization=`, its Amendment tab carries Accept with interpretation / Reject with reason) or PromotionPanel (`?panel=promote&evolution=`) with the gates summary "4 pass · 1 unknown" (success tone only when every required gate passes) and, on a 409 stale-base, the recovery line: the fork's base is behind the head, so redo the work against the new head and `artyfact submit` again (there is no rebase command). `?candidates=a,b` (global) preselects candidates for composition; the Map's "overlap · N" chip links there. Empty: "Nothing is waiting on you." "Waiting for you" is defined once: one decision per open realization, an app candidate submitted, evaluated or selected (stale included) or a Genome amendment awaiting an admin; the promotion row is where a candidate is decided, not a second item. The queue heading, the rail count (`useReviewCount`), the Overview "N waiting for review" line and the Work card's "N await review" count it from the same queries (`useReviewQueue`), and the worker reports the same set as `SystemSummary.realizationCounts.awaitingReview` for Home. The Inspector's "Open in Review" / "in N candidates · overlap" uses the same queries. With `?candidates=` and no row selected, the right pane lists the selection with its Evolution and a "Promote <Evolution>" link when all belong to one Evolution. Works under `/things/:thingId/review`.

**Import review** is two-state: pending until an admin accepts, then accepted. Accepting with rejected nodes removes them from the Genome in the same step (backend.md B.10); the outcome reads "N rejected node(s) were removed from the Genome (System commit abc1234)" and links the removal amendment, and `warnings` list live Evolutions whose criteria the removal deletes. "Reject import" stays disabled until the platform has a reject route. **Amendment review** (CandidateReview's Amendment tab) shows the same agreement tree, read-only once the realization is decided, keyed on the reviewed commit; an agreed node's ops that depend on a rejected node say "needs <title>".

## C.7a Home
`/` is outside the System layout: its own header (wordmark, fixture pill and Retry, admin token, "Go to… ⌘K"), `h1 Systems`, a "Needs you" ledger and one card per System from `GET /api/systems`. Everything is computed client-side from that response.

**Needs you.** One row per System with something pending, each a link: "<System> · N await your review" (the server's `awaitingReview`, the rail's number) and "<System> · import awaits review" to that System's head Review, "<System> · N tasks await an agent", "a plan awaits promotion" and "N tasks await selection" (from `SystemSummary.planCounts`: `awaitingAgent`, `integrated`, `submitted`) to its Work, "<System> · deployed, behind" and "<System> · deploy failed" to its Deployments. Row text is attention-toned (danger for a failed deploy). With nothing pending the section is one quiet line, "Nothing is waiting on you." It is plain text, so reduced motion and effects off read identically.

**Card.** System name, id and Phase; one headline sentence by precedence awaiting review > import pending > tasks await an agent > plan awaiting promotion > tasks await selection > evolving > not built > quiet ("3 await your review", "2 tasks await an agent", "2 realizations evolving", "not built", "quiet"); one deploy line with the latest build folded in ("deployed · build passed", "deployed, behind", "× deploy failed", "deploying", "not deployed, unknown"); head sha and updated time. Success colour appears only when the build passed. Beside the card, "Describe a change" and, when something awaits, "Review" (and "Work" when plans need an agent or a promotion). `observed` is not shown on the card.

**Rail.** Side navigation shows "Review, n waiting" and "Work, n waiting", where Work counts `awaitingAgent + submitted + integrated` from the System's live `GET /api/systems/:id` (the cached systems list can be stale).

**Order.** Cards sort by attention, then evolving, then most recently updated. `cardSummary()` in `views/home/signifiers.ts` produces the headline, tone, deploy line and review link; `needsYou()` produces the ledger rows.

**Go to… ⌘K.** Opens a Home-scoped palette over Systems and shared Parts (Home has no System model, so it does not reuse the System palette's index). An empty API shows an empty state with the `artyfact init` hint; an unreachable API falls back to the bundled fixture.

## C.7b Code
Genome and App tabs, a revision picker, a file tree and a CodeMirror pane. Editing is on head only. Edits are a local draft; Commit… opens a sheet (message, why, Evolution or a new one, name, admin token). The commit starts an editor realization and goes to the fork over Git, then lands on Work as a candidate. A Genome commit becomes `awaiting-admin`. The Inspector's "Open in Code" links the node's source document.

## C.11 Tests
vitest jsdom: model index (`screen.people` children, `entity.ContactRecord` storedIn), status (not-run ≠ pass), useSelection, useMapGraph, useJourneyGraph (J.connect: failure edges, 3 lanes), PromotionPanel disabled/stale. Playwright per route with axe: overview P1 + three meters; map deep link breadcrumbs + grey badges; journeys J.contacts failure edge + inspector; theory T1–T5; work evolution.1 Start work → packet; evaluations/changelog empty states never green.
Three Playwright modes: fixture (default, port 1338, `/api` 404s), fake (`ARTYFACT_E2E_FAKE=1`, port 1339, `FAKE_ARTIFACTS=1` and `ADMIN_TOKEN=test`, specs tagged `@fake`, run one at a time against one in-memory platform) and live (`ARTYFACT_E2E_LIVE=1`, `@live`). The fake specs drive five use cases through the UI: Home, describe a change (Evolution, packet, editor commit, build unknown until a reported preview, health assay), edit and realize (Inspector to Code, commit, accept, Changelog, Home), Compare, and runtime events on Deployments. A second fake server (port 1340, `FAKE_SEED=artyfact`) serves the self-model specs: Artyfact's own Genome on Home, every view without console errors, and an intent under the platform Thing. Further specs cover describing a change by intent (message, routed path, op toggle, accept, candidate, Evolution, packet scope from node `files`), Review (queue rows by kind, the rail's "Review, n waiting", a candidate review, the promotion desk's gates summary and disabled reasons, reject and accept amendments, a candidate turning stale behind the new head) and a sweep of every view on Peopling. Each visited page is checked with axe and for green that is not a pass. `e2e/iteration2.live.spec.ts` repeats the loop against a deployment when `ARTYFACT_ADMIN_TOKEN` is set (`ARTYFACT_CI=1` also waits for a CI build).


## Parts and single-Thing entry (accepted contract)

Home has distinct Systems and reusable Parts sections. System-private Parts stay in their System. Opening a one-Thing System enters the full Thing workspace with a System breadcrumb and explicit overview; the side rail serves the Thing scope (there is no page-level "Thing views" nav), and the page keeps the breadcrumb, the Things switcher and its cards; direct Thing links remain stable when more Things are added. The browser inspects pinned Parts, provenance, source and realized artifacts, and associated Phenome evidence. Authoring remains in CLI/agents.

Public `/`, `/model`, and `/connect-agent` explain ontology import or agent authoring, source mapping, Genome-only Evolution review, Realization Tasks and integrated implementation review, followed by base deployments/metrics/flags and optional outcomes. They preserve Genome-first Things, optional Parts and source versus realized output without presenting Genome/Proteome/Phenome as sequential build stages. Keep Bring your agent primary and preserve prerendered/no-JS content, accessibility and reduced motion. Document only shipped commands. See [GRREAT](../grreat/roadmap.md) for acceptance and progress.
