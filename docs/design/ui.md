# Appendix C — UI design (apps/platform/src)

## C.0 Foundations
react-router 7 data mode; routes `/` (Home), `/s/:systemId/r/:rev/{overview,map,journeys,theory,code,work,review,evaluations,changelog,compare,phenome}`, each also under `…/things/:thingId/` (`/s/:systemId` opens the sole Thing's workspace when the System has one Thing, else head's overview; `…/history` redirects to `…/changelog` and `…/work?panel=promote` to `…/review?panel=promote`, both keeping every param and the hash); global params `focus`, `layer`, `candidates` preserved by nav links; view-specific `journey`, `step`, `evolution`, `realization`, `panel`, `evaluation`, `commit`, `repo`, `path`, `from`, `to`, `level`, `deployment`, `build`. The fixture fallback applies only when the API is unreachable; a reachable, empty API shows Home's empty state. TanStack Query 5 for all API calls (poll `/work` 5 s or SSE). `src/api/client.ts`: getModel, getEvolutions, getEvaluations, getHistory, getPacket, startWork, submit, promote; fixture fallback. `src/model/`: `useModel()` {model, byId, children, parent, crossLinks, criteriaFor, rollup}, `useSelection()` {focusId, setFocus(id,{view?}), layer, setLayer, candidates, setCandidates}, `status.ts` verdictOf/rollup (only pass → success colour). `NodeChip` kind→glyph for all kinds.

## C.1 Shell
TopBar: Wordmark (Georgia, links to Home), SystemRevisionSelector (+ state pill canonical | candidate | deployed, options from `GET …/revisions`), PhaseBadge, ⌘K CommandPalette (cmdk over byId). The layer switch (label "Overlay") lives in the Map header. SideNav: Overview, then one group per layer, Private Parts last. Each group is headed by the layer name (its accessible label) with the layer's question beneath in quiet sentence case (its accessible description): Genome, "What should it be" (Map, Journeys, Theory, Code); Proteome, "What is being made" (Work, Review, Evaluations, Changelog); Phenome, "What does it do" (Deployments). The Overview meters carry the same three questions (`LAYER_QUESTIONS` in `model/kinds.ts`). Review shows a count after its label when decisions wait, including a pending import review (attention tone, hidden at zero, link named "Review, n waiting"). Work does the same for Evolutions whose plan is ready or has tasks awaiting an agent (`useWorkCount`, "Work, n waiting"). Compare is not on the rail; it opens from a Changelog row's "Compare with parent" and `g x`. Inside a Thing workspace the rail links resolve to `/things/:thingId/<view>`; there is no separate Thing workspace link. Under 640px the rail collapses to glyphs and keeps the three layer heads visible. Go-to keys: `g o m j t c w r e l x d` (`g h` still opens the Changelog). Main Outlet. InspectorDrawer right 380px resizable, open when focus set; Esc closes; `[`/`]` siblings; `g m`/`g w` shortcuts. Grid `auto 1fr auto`.

## C.6 Work
EvolutionBoard columns by state; EvolutionCard scope chips, "≈ overlap" when any of its candidates conflicts and "N await review" (attention) when candidates or amendments wait; a plan line (attention) from `plan` via `taskSignals()` in `views/work/plan/signals.ts`: "plan ready · 4 tasks in 2 waves", "wave running · 2 of 3 tasks", "1 task awaits an agent" (counts only: a running wave and blocked tasks need the full plan, so the card does not claim them); RealizationRow (agent, role, local/hosted, status, fork + short sha, last checkpoint or "unknown", changed subjects, ConflictChips typed, inline "Review" toggle, "Open in Review"); StartWorkPanel → PacketViewer (markdown, copy, CLI line, token countdown); inline CandidateReview tabs Semantic delta / Files / Evaluations / Amendment, "select for composition" → `?candidates=`. "Promote in Review" is a link to Review's desk (`/review?evolution=E&panel=promote`, keeping `?candidates=`); `/work?panel=promote` redirects there. The card's "N await review" counts candidates, stale candidates and amendments, not the promotion row.

**Plan** (`views/work/plan/`, `PlanPanel`; `?panel=plan`, header button "Plan" before "Start work"). The full `TaskPlan` comes from `GET …/evolutions/:eid/plan` (query `qk.plan`, polled 5 s and invalidated by `task.updated`, `plan.updated`, `checkpoint`, `realization.updated`); the board payload carries only `plan` counts. No plan (404) → "No plan yet." and "Plan tasks" (`POST`), disabled with its reason on fixture data or before the Evolution is approved. Toolbar: "4 tasks · 2 waves", "Re-plan" (inline confirm, `POST {force: true}`, disabled once a task has started), "Merge selected" (two or more planned tasks ticked). `WaveBoard` reuses the board columns: "Wave 1 · 3 tasks" and "Start wave 1", disabled with the `canStartWave` reason (fixture, Evolution not actionable, no planned task in the wave, an earlier wave not promoted). `TaskCard`: title (opens `?task=`), `TaskStatus` chip (`planned ○ claimed ◔ realizing ◑ evaluated ◕ promoted ● blocked ⊘`; blocked is derived from dependencies not promoted and is attention, claimed attention, nothing pass), up to four node chips, "6 files · 2 entry", "depends on" titles, `ConflictChips` naming the other task (`→ declared`, `§ file`, `≈ soft-semantic`), "awaits an agent" when claimed. `TaskDetail`: title and intent (Save task), "Why wave n" (dependencies and overlaps with earlier waves), Footprint (nodes, globs, paths, unmatched, entry files, muted "Computed from the nodes' files bindings"), criteria with `VerdictBadge`, dependencies (open that task), status with claim label and the realization (opens its review), Split (move ticked nodes to a new task; dependents depend on both). Merge and split are pure list edits in `plan/lib.ts`; every edit sends the whole list without footprints in `PUT …/plan` and the server recomputes footprints, conflicts and waves. "Start wave n" (`POST …/waves/:n/start`) shows `WaveStartPanel`: per started task its `PacketViewer` (packet, one-time command, copy-once, token countdown), "Copy all commands", and the skipped tasks with the server's reason. Admin writes use the header token. Fixture data shows a read-only sample plan for `evolution.1` (`plan/sample.ts`) with every write disabled and the standard reason.

## C.6a Describe a change by intent
`?panel=intent` on Work (`views/work/intent/`): a message, optionally anchored on a node, becomes a Proposal (routed path, the agreement tree over its ops, questions with inline replies). While the panel is open it replaces the Evolution board and detail; its head shows the anchor as a node chip with "Clear anchor", and "Back to board" closes it and keeps the other params. "Describe a change" is the one label at every entry (Work header, Home card, Inspector, Code file pane) and the Work header's one primary action; "+ Evolution" is a secondary text button. The UI is driven by template view hints, not by node kind (`docs/design/ontology.md`).

**Agreement tree** (`intent/agreement/`, `AgreementTree`): `Proposal.plan` as rows rooted at Things, each with the kind glyph, title, counts ("3 add · 2 update · 1 remove" over its subtree), the rollup word (agreed, rejected, deferred, mixed, undecided) and Agree / Reject / Defer toggles (`aria-pressed`, named "Agree <title>"). An open node shows its own ops' diffs; no per-op checkboxes. Children inherit a node's decision; deciding a node clears its descendants' decisions, and a child decided afterwards overrides it (the parent shows "mixed"). Backspace or a second click clears a node's own decision. A node with an `error` problem cannot be agreed; an agreed op that needs a rejected or deferred one is left out and its node says "needs <title>". Decisions persist through `PUT …/intents/:pid/decisions` (optimistic, rolled back on refusal); a proposal without a stored plan gets one from the model index (`planFromOps`) and keeps decisions in the view. Rule styles, never green: agree solid apricot, reject dashed with secondary text, defer dotted with a "deferred" chip, mixed at half strength. All open when at most five nodes own ops, else only the Things. Keyboard: one tab stop with roving focus; ↑↓ move, → opens or enters, ← closes or goes to the parent, Home/End, Enter/Space open and close, `a` `r` `d` decide, Backspace clears; a hint line under the tree says so. Variant `genome` (import and amendment review) has no Defer. Fixture: every decision disabled, the tree still navigable.

**Accept agreed** sends the agreed, unblocked ops; it is disabled with a reason while any node is undecided or nothing is agreed. The summary reads "11 of 14 changes agreed · 1 deferred · 2 rejected". Without deferral, accept opens the candidate on Work. With deferred nodes the platform moves their ops to a new proposal and the panel stays open: "Accepted 11 changes into <Evolution>. 3 deferred changes wait in this proposal." with "Continue with deferred" (opens that proposal) and "Open the candidate".

## C.6b Review
`/review` (`views/review/`), the operator's inbox and promotion desk, two panes. Left, the decision queue ("Waiting on you N"), grouped by Evolution, one row per pending decision: `import` (the System's import review is pending, `SystemSummary.importReview`), `candidate` (submitted/evaluated, not promoted or rejected), `stale` (its base is behind head, dashed attention), `amendment` (Genome realization `awaiting-admin`), `promotion` (an Evolution with an evaluated candidate on the current head). A row shows the kind word, agent and role, candidate id ("selected for composition" when it is in `?candidates=`), ConflictChips (one per kind, with the count) and "base = head" (neutral), "behind by N" or "behind head" when the distance is unknown (attention); a promotion row reads "ready to promote". An import row reads "Import · 121 nodes", "awaits an admin" and the Genome commit, with an attention rule on its left; it is its own group, "Import", before every Evolution, because new Evolutions, realizations and intents are refused (409 `import-unreviewed`) until it is accepted. The queue takes the summary's pending status unless the review itself (`GET …/import-review`) says accepted. Within a group: amendments, then candidates, then the promotion row. Right, the selected row: the import review (`?panel=import`, `GenomeReview`), CandidateReview (`?evolution=&realization=`, its Amendment tab carries Accept with interpretation / Reject with reason) or PromotionPanel (`?panel=promote&evolution=`) with the gates summary "4 pass · 1 unknown" (success tone only when every required gate passes) and, on a 409 stale-base, the agent's recovery line: rebase the fork on the new head and `artyfact submit` again (the CLI has no rebase command). `?candidates=a,b` (global) preselects candidates for composition; the Map's "overlap · N" chip links there. Empty: "Nothing is waiting on you." The rail count (`useReviewCount`, the queue's own row count, import included), the Overview "N waiting for review" line and the queue heading count every row, promotion rows included; the Work card signals and the Inspector's "Open in Review" / "in N candidates · overlap" derive from the same queries (`useReviewQueue`). With `?candidates=` and no row selected, the right pane lists the selection with its Evolution and a "Promote <Evolution>" link when all belong to one Evolution. Works under `/things/:thingId/review`.

**Import review** (`views/work/panels/GenomeReview.tsx`, pure helpers in `views/review/importReview.ts`): the imported head Genome from `GET …/import-review` as an `AgreementTree` (variant `genome`: Agree / Reject, children inherit, every node new so rows carry no counts), the summary "121 nodes: 120 agreed · 1 rejected" (and "· N undecided"), the readiness findings (errors first, the first twelve then "Show all N") and the unmapped app paths, then the Decision: admin token, "Accepted interpretation" (required) and "Accept import" (named "Accept import, remove N rejected" when any are). Accept sends `rejectedNodes`, every effectively rejected node (own or inherited); it is disabled with a reason while any node is undecided or an agreed node sits under a rejected one (its removal would take the agreed node too). The result says the rejected nodes will be removed by an amendment awaiting an admin and links that amendment's row. "Reject import" is shown disabled with its reason: the platform has no reject route yet. An accepted review shows its recorded interpretation and rejections, the tree read-only. Fixture: every decision and accept disabled with a reason; a System imported without a review says "This System has no import review."

**Amendment changes** (`AmendmentReview`, Amendment tab): the "Changes" section replaces the Semantic delta list with an `AgreementTree` (variant `genome`) built client-side by `planFromDelta` over the review's delta and the model index ("1 add" on the section that gains a node); an open node shows its changes' before/after field diffs. Decisions stay in the view. Accept stays all or nothing: while any node is rejected, "Accept amendment" is disabled with "The platform cannot accept part of an amendment; reject it with the reasons or agree all." and the rejected nodes' titles; undecided nodes do not block accept.

## C.7a Home
`/` is outside the System layout: its own header (wordmark, fixture pill and Retry, admin token, "Go to… ⌘K"), `h1 Systems`, a "Needs you" ledger and one card per System from `GET /api/systems`. Everything is computed client-side from that response.

**Needs you.** One row per pending decision across all Systems, each a link: "<System> · N candidates await review" to that System's head Review, "<System> · deployed, behind" and "<System> · deploy failed" to its Deployments. Row text is attention-toned (danger for a failed deploy). With nothing pending the section is one quiet line, "Nothing is waiting on you." It is plain text, so reduced motion and effects off read identically. Today the review rows and the card's attention headline come from the `awaiting-admin` signifier and `realizationCounts.awaitingAdmin`, which count Genome amendments awaiting an admin; submitted app candidates (`openCandidates`, `pending-realization`) are in that System's Review queue but not yet on Home.

**Card.** System name, id and Phase; one headline sentence by precedence attention > evolving > not built > quiet ("3 await your review", "2 realizations evolving", "not built", "quiet"); one deploy line with the latest build folded in ("deployed · build passed", "deployed, behind", "× deploy failed", "deploying", "not deployed, unknown"); head sha and updated time. Success colour appears only when the build passed. Beside the card, "Describe a change" and, when something awaits, "Review". `observed` is not shown on the card.

**Task and import signifiers.** The headline precedence is awaiting review > import pending > tasks await an agent > plan ready > wave running > evolving > not built > quiet, from `signifiers[]` (`import-pending`, `task-awaiting-agent`, `plan-ready`, `wave-running`) with `taskCounts` and `importReview`: "import awaits review", "2 tasks await an agent", "a plan is ready", "wave running". The first four are attention-toned; wave running reads as evolving. Needs-you rows: "<System> · import awaits review" to Review, "<System> · 2 tasks await an agent" and "<System> · a plan is ready" to Work. A card shows a "Work" action beside "Review" when a plan or its tasks need a person (`workHref`).

**Order.** Cards sort by attention, then evolving, then most recently updated. `cardSummary()` in `views/home/signifiers.ts` produces the headline, tone, deploy line and review link; `needsYou()` produces the ledger rows.

**Go to… ⌘K.** Opens a Home-scoped palette over Systems and shared Parts (Home has no System model, so it does not reuse the System palette's index). An empty API shows an empty state with the `artyfact init` hint; an unreachable API falls back to the bundled fixture.

## C.7b Code

The Inspector's "Open in Code" links the node's source document.

## C.11 Tests
vitest jsdom: model index (`screen.people` children, `entity.ContactRecord` storedIn), status (not-run ≠ pass), useSelection, useMapGraph, useJourneyGraph (J.connect: failure edges, 3 lanes), PromotionPanel disabled/stale. Playwright per route with axe: overview P1 + three meters; map deep link breadcrumbs + grey badges; journeys J.contacts failure edge + inspector; theory T1–T5; work evolution.1 Start work → packet; evaluations/changelog empty states never green.
Three Playwright modes: fixture (default, port 1338, `/api` 404s), fake (`ARTYFACT_E2E_FAKE=1`, port 1339, `FAKE_ARTIFACTS=1` and `ADMIN_TOKEN=test`, specs tagged `@fake`, run one at a time against one in-memory platform) and live (`ARTYFACT_E2E_LIVE=1`, `@live`). The fake specs drive five use cases through the UI: Home, describe a change (Evolution, packet, editor commit, build unknown until a reported preview, health assay), edit and realize (Inspector to Code, commit, accept, Changelog, Home), Compare, and runtime events on Deployments. A second fake server (port 1340, `FAKE_SEED=artyfact`) serves the self-model specs: Artyfact's own Genome on Home, every view without console errors, and an intent under the platform Thing. Further specs cover describing a change by intent (message, routed path, op toggle, accept, candidate, Evolution, packet scope from node `files`), Review (queue rows by kind, the rail's "Review, n waiting", a candidate review, the promotion desk's gates summary and disabled reasons, reject and accept amendments, a candidate turning stale behind the new head) and a sweep of every view on Peopling. Each visited page is checked with axe and for green that is not a pass. `e2e/iteration2.live.spec.ts` repeats the loop against a deployment when `ARTYFACT_ADMIN_TOKEN` is set (`ARTYFACT_CI=1` also waits for a CI build).


## Parts and single-Thing entry (accepted contract)

Home has distinct Systems and reusable Parts sections. System-private Parts stay in their System. Opening a one-Thing System enters the full Thing workspace with a System breadcrumb and explicit overview; the side rail serves the Thing scope (there is no page-level "Thing views" nav), and the page keeps the breadcrumb, the Things switcher and its cards; direct Thing links remain stable when more Things are added. The browser inspects pinned Parts, provenance, source and realized artifacts, and associated Phenome evidence. Authoring remains in CLI/agents.

Public `/`, `/model`, and `/connect-agent` explain Genome-first Things, optional Parts, and source versus realized output without presenting Genome/Proteome/Phenome as sequential build stages. Keep Bring your agent primary and preserve prerendered/no-JS content, accessibility and reduced motion. Document only shipped commands. See [GRREAT](../grreat/roadmap.md) for acceptance and progress.
