# Genome lifecycle implementation

Accepted 2026-10-13. This specification implements the user-approved story and platform plan.

## Decisions and invariants

- An Evolution changes only the Genome. Approval commits the exact reviewed Genome delta. It does not implement, deploy, or change live flags.
- A Realization is implementation of a pinned accepted Genome revision. A new Realization can target an existing revision without a new Evolution.
- Realization -> Tasks -> agent attempts. A Task owns one artifact binding, one isolated fork, steps, dependencies, ontology read/write scope and checks. One writing attempt is active at a time; retries preserve work and replace credentials.
- Agents run in the user's local harness. Artyfact owns durable plans, scheduling constraints, review, provenance, and permissions.
- Task results integrate into one candidate per changed artifact binding and one reviewed implementation manifest. Promotion preserves the current accepted Genome and records the Genome actually realized per binding. Later overlapping Genome changes require explicit replan; disjoint advances must not silently retarget work.
- Native ontology packages and agent-converted sources are reviewed before acceptance. Domain vocabulary is open; effects/events/assays are an optional outcomes pack. Base Phenome supplies deployments, runtime/custom metrics and Cloudflare Flagship controls.
- Keep all existing historical records/IDs/routes readable. Do not reinterpret legacy implementation/mixed Evolutions as Genome amendments. New contracts are additive; UI names current agent-level realizations Task Attempts under new plans.
- Source scope includes artifact/repository identity, not just path. Missing scope evidence means independence unknown. Read/read sharing can be independent; writes, contracts, explicit dependencies and inherited scope determine interference.
- Preserve authorization, exact-candidate evidence, fail-closed checks, user changes, accessible UI and truthful capability labels. Never merge with red CI.

## Contract addendum: Genome review and planning (port of tasks-integration)

Added 2026-10-13. Additive; old rows and older servers stay readable. Wire types: `shared/api.ts`, `shared/lifecycle.ts`.

- **Proposal agreement tree.** `Proposal.plan` (required on the wire, `[]` for rows older than plans) and `deferredFrom` read from the `proposals` columns `plan_json`, `decisions_json` and `deferred_from`. A node's `path` runs from the System root down to and including the node. Decisions are explicit per node; inheritance, pruning and deferral are the Worker's (`worker/intents.ts`). With no stored decisions an accept takes any op ids.
- **Proposal plan writes.** `setProposalPlan(pid, plan, decisions, deferredFrom?)` is one conditional UPDATE that writes only while the row is `open`; it returns false for `accepting`, accepted, abandoned or unknown rows. An omitted `deferredFrom` keeps the stored one. `createProposal` writes the columns in the create transaction, and a revision that carries `plan` replaces the tree and keeps the decisions. None of these emit events.
- **Deferred rebase.** `rebaseProposal(pid, oldBase, newBase)` is one conditional UPDATE of `provenance.genomeCommit`. It requires the row to be `open`, have `deferred_from`, still sit on `oldBase` and hold no staged approval. The Worker re-validates the ops on `newBase` first. It emits nothing.
- **System import review.** One row in table `import_review`. `setImportReview(review | null)` replaces or clears it in one transaction, then emits `system.import-review` (`status`, or null on clear) and `system.updated` when a row changed. `casImportReview(expectedStatus, expectedGenomeCommit, next)` is one conditional UPDATE in one transaction, so concurrent accepts succeed once and an accept never overwrites a review a re-import opened. It emits the same two events only on success. The summary carries `importReview {status, genomeCommit, nodes}` and the signifier `import-pending` while pending.
- **Plan counts.** `SystemSummary.planCounts` is computed on read from `realization_plans` (`worker/do/plan-summary.ts`). `open` counts plans not promoted. `awaitingAgent` counts tasks of open plans that claim would accept now: pending with every dependency selected, or claimed or working with a lapsed lease, and no conflicting task with a live attempt. `submitted` counts tasks whose candidate awaits selection. `integrated` counts plans awaiting promotion. The signifier `tasks-awaiting-agent` appears while `awaitingAgent > 0`, and `plan-awaiting-promotion` while `integrated > 0`. Plans emit no SSE events; clients poll.
- **Registry freshness.** `GET /api/systems` reads registry rows, so its `planCounts` and `importReview` are only as fresh as the last `refreshRegistry(env, systemId)` (`worker/service.ts`). A lapsed lease changes `awaitingAgent` with no write at all. Every lifecycle write must call `refreshRegistry` after it lands: create, claim, start and resume, attempt end, select, integrate, submit and promote. P3 owns those calls; main already refreshes on submit and promote. Every import-review write must call it too: import, accept and its rollback. P4 owns those. `GET /api/systems/:id` reads the DO live, so the SPA should use it where counts must be current.
- **Planner draft.** `POST lifecyclePaths.draft(systemId)` takes `DraftRealizationPlanRequest` and returns `DraftRealizationPlanResponse`. It persists nothing, and its `request` posts unchanged to create.
- **Packet.** `LifecycleTaskPacket` gains optional `wave` (1-based), `independence`, `doNotTouch`, `concurrent`, `buildsOn` and `agentsMd`, and keeps `markdown`.
- **Error codes.** `import-unreviewed` (409) and `rejected-node-referenced` (422). Invalid task lists stay 400 `bad-request` on create, and the draft reports cycles and invalid nodes as `problems`.
