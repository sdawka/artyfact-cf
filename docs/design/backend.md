## B.2 SystemAuthority SQLite + RPC
```sql

system_commits(id PK, parent, manifest_json, manifest_hash, evolution_ids, decision_json, created_at)
evolutions(id PK, title, status, kind, base_commit, scope_json, criteria_json, affected_nodes, created_at, decided_at)

checkpoints(realization_id, seq, message, commit_hash, created_at, PK(realization_id, seq))
candidates(id PK, realization_id, commit_hash UNIQUE, manifest_json, changed_paths, changed_nodes, created_at)
evaluations(id PK, candidate_id, criterion_id, hook_id, execution, verdict, observations_json, evidence_key, verifier, created_at)
events_seen(event_id PK, seen_at)
```
`promote` runs in `transactionSync`: read head, compare to `expectedHead` else throw `StaleBaseError{currentHead}`; require every required-gate criterion of the candidate to have `verdict=pass, execution=completed`; compose manifest `{genomeCommit, artifacts:{'artifact.webapp':{repo,commit}}, templateVersions, hookVersions}`; SHA-256 canonical JSON; insert system_commit parent=head; update head; sibling candidates → rejected; evolution → promoted. Promotion changes the manifest, not git.

## B.3 Artifacts usage
Namespace `artyfact`; repos `<slug>.genome`, `<slug>.app` (Peopling: `peopling.*`), forks `<repo>--rN`, plus the `platform` meta repo (slice 2.7, see `apps/platform/README.md`). Bootstrap via `npx artyfact init` (`scripts/bootstrap.sh` wraps it for the example); Worker import = `ARTIFACTS.get(name)` → `log({limit:1})` → DO.bootstrap. `loadGenomeAt(env, repo, commit)`: `using r = await env.ARTIFACTS.get(repo)`; walk `readCommit→readTree` recursively, `readFile` each → `loadGenome(files, {revision: commit, templates})` (a v1 revision is 422 `legacy-genome`); cache parsed JSON in DO keyed by commit. Realization: `base.fork(name, {defaultBranchOnly: true})`, poll `info()` until `ready`, `createToken('write', 21600)`. On submit: `readCommit(commit)` validates; `diffTrees(repo, base, commit)` by comparing tree-entry hashes recursively → changedPaths; the Genome nodes' `files` (`sourceMapFor`, ontology.md §3) → changedNodes (`unmapped:<path>` for misses). Genome amendments go through forks of `<slug>.genome`; admin accept records the fork commit as the new `genomeCommit`. No isomorphic-git in the Worker. Editor writes (`worker/git/`, `worker/editor.ts`): the binding cannot write, so the Worker builds blobs, the rewritten trees along edited paths (untouched subtrees reused by id) and the commit itself, then pushes over smart HTTP `git-receive-pack` (v1, `report-status`, undeltified pack v2) with a write token minted per commit (ttl 300 s, revoked in `finally`); the ref must still be the expected parent, and Artifacts' `ng … stale ref` maps to 409 `stale-head`. The commit then goes through the normal `submit` (source `ui`); once the candidate exists, its push event is marked seen so the queue acks that delivery as a duplicate (if submit fails, the queue still submits it). Commits are capped at 8 MB in total, and files over the 512 KB read cap cannot be edited in place.

Git push, builds, deployments and the Phenome (iteration 2): editor commits are pushed over smart HTTP (above); `FAKE_ARTIFACTS=1` swaps in an in-memory Artifacts namespace and a fake receive-pack (`worker/artifacts/fake-platform.ts`) so the whole loop runs without an account. `builds` and `deployments` (`worker/do/builds-store.ts`) link build, candidate, realization, Evolution and System commit both ways. `phenome_events` (`worker/do/phenome-store.ts`) stores events a deployed app reports with `PhenomeEventHeader` (`POST /systems/:id/phenome/events`, bearer = deployment ingest token, realization secret or admin; 100 events and 8 KB per event, 5000 rows per System, duplicates dropped by `id`). The CI Worker is described in [`docs/ci.md`](../ci.md).

## B.4 Protocol & hooks
Intent routes (admin): `POST /systems/:id/intents {message, anchor?}`, `GET /intents/:pid`, `POST /intents/:pid/reply` and `POST /intents/:pid/accept {opIds}` route and translate a message into ops with the ontology engine, then accept as a Genome amendment candidate. Proposals live in the System DO. Details, errors and the stale-base rule are in `docs/design/ontology.md` §5.

`POST /systems/:id/evolutions {title, intent, kind?, risk?, affectedNodes?, acceptanceCriteria?}` (admin) creates an actionable Evolution; an absent or empty `affectedNodes` is an unconstrained scope (the packet permits every path except the protected ones), and absent `acceptanceCriteria` default to the System's criteria whose `targetKind` matches the Evolution's target (`artifact`/`runtime` for an explicit `implementation`, otherwise `model`: with `kind` absent or `mixed` the target is unknown, and app criteria stay blocking on, but could never pass for, a Genome candidate).

`POST /evolutions/:id/realizations {agentLabel?, target?}` (admin) → fork + token + realization secret (only its SHA-256 is stored; required as a bearer on the realization's checkpoint/submit/sync/status/packet routes, revoked on reject) + packet (JSON + markdown: intent, acceptance criteria, Genome excerpts for affected nodes, journeys, commitments, permitted/protected paths, entry files with certainty, commands, concurrent work, submit instructions, hash). Submission by CLI `POST /submit {commit, previewUrl?}` or Queue `cf.artifacts.repo.pushed` → resolve fork → `submit(id, head, 'event')`; idempotent on (realization, commit); `events_seen` dedupes.
Template upgrades (`worker/template-upgrade.ts`): `GET /systems/:id/template-upgrade?ref=head` → `TemplateUpgradePlan {template, from, to, upToDate, files[{path, action, reason}]}`, comparing blob ids of the current scaffold (`platform:templates/<template>/scaffold.yaml` → repo + path, head), the app at `ref`, and the app's `.artyfact/template.json` lock: missing in the app → `add` (`conflict` if the lock had it and the template changed it); untouched since the lock and changed in the template → `update`; dropped by the template and untouched → `remove`; edited by the app (or no lock) and changed in the template → `conflict`; unchanged in the template since the lock → omitted. CLI ignore rules apply (README, secret files, node_modules, dist). `POST` (admin) `{include?}` applies the non-conflicts plus the included conflicts and the new lock: `createEvolution` ("Upgrade app template to <short>", kind `implementation`) → `startWork` (`human:template-upgrade`, role `author`, origin `editor`) → `commitEdit` with `expectedHead` = the planned app commit; 409 `up-to-date`.

Builds and deployments (iteration 2, [`docs/ci.md`](../ci.md)): a new app candidate dispatches the `artyfact-ci` Workflow (optional `env.CI`); CI, agent or admin build reports land in `builds`; a passed preview with a URL re-enters `submit(…, {commit, previewUrl}, 'ci')` so `C.webapp.health` runs; `promote` records a pending production deployment that a passed production report sets `live`.
| hook | criterion | verdict |
|---|---|---|
| exists | C.webapp.exists | required files present & non-empty at commit |
| scope | C.system.promotion | changed ⊆ permitted; `system/**` in app realization → fail; unmapped → unknown |
| genome-amendment | C.system.structure | loadGenome on fork `system/` valid → status awaiting-admin |
| overlap | C.system.readiness | ConflictReport{file \| soft-semantic \| hard-semantic \| evidence} across concurrent candidates; via `overlap()` |
| health | C.webapp.health | fetch `previewUrl/health`, compare buildId; no URL → not-run/unknown |

Hook selection (`worker/hooks/run.ts`): affected criteria = the Evolution's acceptance criteria ∪ criteria whose `subjectId` is in the candidate's changed nodes ∪ System criteria gated on `submission` ∪ every criterion that blocks this candidate's promotion (promotion-gated, hard, with a bound hook; model-targeted only for a Genome candidate), so the gate never waits on evidence nothing produces. Subject matching is exact: there is no ancestor or descendant expansion. Genome authors must bind each criterion to the node that the source map reports for the files realizing it. Every hook of an affected criterion yields an Evaluation. Hooks the platform cannot run come back `not-run/unknown`.

## B.5 Composition & promotion
`GET /evolutions/:id/candidates` (candidates + evaluations + conflicts). `POST /systems/:id/promote` revalidates exists+scope on the exact commit then CAS. Two complementary candidates: `artyfact compose r1 r2` on the user's machine (fork `<slug>.app--cN`, push merged tree, submit as composed candidate bound to both). `GET /history` newest-first (an alias of `GET /changelog` for one release).

Changelog and compare (`worker/compare.ts`, `worker/changelog.ts`): `resolveRef(scope, ref)` maps `head`, `sc-N`, a candidate id, a recorded 40-hex commit or a realization id (fork head) to `{repo, commit}` for the app or the Genome; an accepted Genome commit resolves to the fork that holds it. App files are compared across repos by tree hash (`diffTreesAcross`): git objects are SHA-1 content-addressed, so equal hashes in a fork and its base mean equal content. Path nodes come from the source map at `to`. A changelog entry is a System commit against its parent (the root import against nothing, so every node and file is added) plus per-criterion folded verdicts before/after and code links; rows and entries are cached in `changelog_cache` because System commits are immutable. Builds and the deployment are attached at read time.

## B.6 CLI
Lifecycle commands (`packages/cli/src/lifecycle.ts`, README "Genome lifecycle and local agents"): `plan draft|create|show|tasks|list|integrate|review|promote`, `task claim|start|resume|status|checkpoint|submit|select`, `evolution propose|create|show`, `ontology …`. `plan tasks` prints task, status, wave, depends-on, write nodes, footprint, conflicts and the next claimable task. The historical `start|checkpoint|submit|compose` commands read `.artyfact.json` `{platform, systemId, realizationId, forkRepo, remote, tokenExpires, packetHash}`.
A Task workspace is `git clone -c http.extraHeader="Authorization: Bearer <t>" <remote> <dir>` plus `TASK_PACKET.md`, `AGENTS.md` and `.artyfact-task.json`, all excluded via `.git/info/exclude`. `task claim|start|resume` store the fork write token and attempt secret in `.artyfact-task.json` (mode 0600, outside the fork's tracked files, never printed and scrubbed from the packet files), so `claim`, then an agent started with `env -u ARTYFACT_ADMIN_TOKEN`, then `submit` needs no handoff; `submit` uses `ARTYFACT_TOKEN` when set, else the stored token. The target directory is validated before any request. `AGENTS.md` is the packet's `agentsMd`. Remote URL form `https://<ACCOUNT_ID>.artifacts.cloudflare.net/git/<ns>/<repo>.git`.

## B.9 Realization plans, tasks and claims
Routes (`shared/lifecycle.ts` `lifecyclePaths`, `worker/routes/lifecycle.ts`, logic in `worker/lifecycle-service.ts`): `plans` POST create, `draft` POST, `plan` GET, `review` GET, `integrate` POST, `promote` POST, and per task `claim | start | resume | checkpoint | submit | select`. Reads (list, plan, review) follow the System's visibility like `/work`; every write is admin, except checkpoint and submit, which carry the attempt's secret. Task ids follow the CLI's id rule (letters, digits, `.`, `_`, `-`; no leading `-`; not `.` or `..`) because they become directory names and arguments.

Planner draft (`worker/tasks/planner.ts`, `planner-llm.ts`, `tasks/definitions.ts`):
- `POST …/realization-plans/draft {title?, evolutionIds?, nodes?, hint?}` (admin) returns `{request, analysis, problems, provenance}` and persists nothing. `request` posts unchanged to create (the route test posts it back and compares the stored analysis). `genomeCommit` is the current accepted Genome, so create answers 409 `stale-base` if it moves. 400 only for a malformed body, 404 with no accepted Genome.
- Scope is accepted Genome Evolutions plus explicit nodes. Named Evolutions must be promoted `genome-amendment` Evolutions. With neither `evolutionIds` nor `nodes`, the draft takes every accepted Evolution some binding has not realized. Realized rule: only a promoted plan, pinned at or after the Evolution's acceptance, whose task wrote the node counts (legacy bindings fall back to their `realizedGenome`). Nodes held by an open plan (planned, implementing or integrated) are skipped with a warning naming the plan; naming the Evolution takes them again, and explicit nodes are always taken. A removed node becomes a delete step on the nearest bound ancestor whose footprint covers its old globs, else a `missing` problem.
- Planner modes (`plannerFromEnv`): `TRANSLATE=0` off, `FAKE_S1=1` fake, `OPENROUTER_API_KEY` OpenRouter (`OPENROUTER_PLAN_MODEL`, else `OPENROUTER_TRANSLATE_MODEL`, temperature 0), else off; `setPlannerOverride` in tests. The fake groups by (artifact, Thing, section); `#plan:split` gives one task per node and `#plan:dep` a dependency chain, read from the hint and every Evolution intent. Off, or a failed reply, gives the fallback: group by artifact, Thing and nearest section, then merge groups whose footprints share a path or glob (`taskFootprint`). A reply can add criteria but never move or drop them; unknown nodes are dropped, a task spanning Things or bindings is split, uncovered nodes get fallback tasks.
- Each task has `artifactId` from the node's Thing source binding, `steps` from the intent, `writeNodes`, one-hop `readNodes`, `checks` (criteria about its nodes plus System-owned ones) and `dependsOn` (planner edges plus the contract dependencies create derives). Problems carry a severity: `error` (scope lost or create would refuse it), `missing` (no task or no files) or `warning` (repaired). Reply edges that close a cycle are dropped, and a cycle among contract links inside one binding merges its tasks.
- Create (`taskDefinitions`) expands nodes over each binding's tree and stores `analysis` from `analyzeTasks` (`packages/model`): footprints, `dependency | source | ontology | unknown` conflicts and waves (wave n is `waves[n-1]`; wave numbers are 1-based on every surface). Invalid lists are 400 `bad-request`.

Packet (`worker/packets/lifecycle-packet.ts`): `LifecycleTaskPacket` keeps `markdown` and adds `wave`, `independence`, `doNotTouch` (other open tasks' write globs minus any that overlap this task's own), `concurrent` (other tasks with a live attempt), `buildsOn` (selected or completed direct dependencies, with `selectedCandidate`) and `agentsMd`. Tasks ordered through others' dependencies are "ordered with", never independent. The packet holds neither the token nor the secret. `agentsMd` lists, in order: task and wave, permitted edits, do-not-touch, concurrent tasks, builds-on (same-binding dependencies are in the base, others are not in the fork), the tasks after it, and the CLI's task commands.

Claims (`claim`, `start` and `resume` share `startLifecycleTask`):
- A claim takes the first attempt; `resume` takes over a lapsed lease, preserves the fork and fences the old attempt with fresh credentials. Claim is allowed when the task is pending with every dependency selected, or claimed or working with a lapsed lease, and no conflicting task has a live attempt (the same rule as `planCounts.awaitingAgent`).
- A refusal is 409 `invalid-state` with `details`: `{blockedOn: [every dependency still unselected]}`, `{by: <agentLabel>}` for a live writer on the task, or `{taskId, by}` for a live conflicting task. The CLI prints "blocked by <tasks> (not yet selected)".
- Credentials are issued with the response only. A failed start ends its attempt. The registry refresh after create, claim, start, resume, select, integrate, submit and promote is best-effort: a failure is logged and never undoes the write.

Integrate and promote:
- `integrate` replays each selected task's delta onto the pinned base per binding (`replayDelta`), and fan-in builds a dependent task's base from its predecessors the same way. `FileChange.type` (`blob | exec | symlink`) sets the entry kind, so modes and symlinks survive; a mode-only change counts as a change, and a gitlink is refused 409 `integration-conflict`. A binding another promotion moved is 409 `replan-required`: create a new plan. There is no rebase.
- `promote` revalidates the exact candidates. A refused gate is 409 `blocked` or `advisories-unacknowledged` with `details {criteria, advisories}`, each a `GateItem` (candidate, criterion, severity, verdict, execution). Evidence binds by bare commit, `<target>@<commit>`, `genome@<genomeCommit>` or the candidate's preview URL, judged per latest evaluation of each criterion.
- Hook selection includes every criterion that blocks promotion (B.4), so a lifecycle gate never waits on evidence that nothing produces; a task's `checks` is the acceptance set.

## B.10 System import review
Routes: `importReview(s)` GET (public, like `/model`) → `SystemImportReview`; `importReviewAccept(s)` POST `SystemImportReviewAccept` (admin) → `SystemImportReviewAcceptResponse`. `ImportSystemRequest.review` (default true) leaves a new import pending; `artyfact init --no-review` and the fake seeds send `review: false`. A bootstrap from an accepted ontology package also imports with `review: false`. Distinct from the ontology package preview (`shared/ontology-packages.ts`), which reviews a package before bootstrap.
Types: `SystemImportReview` (tree of `ProposalPlanNode`, readiness `findings`, `unmapped` paths with `unmappedTotal`), `SystemSummary.importReview`, signifier `import-pending`, SSE `system.import-review`.

Behaviour (`worker/import-review.ts`, store `worker/do/import-review-store.ts`):
- `importSystem` makes one `recordImportReview` call after the bootstrap. A new System commit (first import, forced re-point) stores a new pending review; a re-import that writes no commit keeps the stored one; `review: false` clears a pending review and keeps an accepted one. `tree` is the head Genome's containment tree below the System (roots are its Things, every node "added"), `findings` the readiness findings, `unmapped` the app head's paths no node's effective `files` glob maps (`.artyfact/**` excluded), capped at 200 sorted paths with the full count in `unmappedTotal`.
- While pending, 409 `import-unreviewed` (message names `/s/<id>/r/head/review?panel=import`, details `{genomeCommit}`) refuses: `POST /evolutions`, `/evolutions/:eid/realizations`, `/intents`, `/template-upgrade`, and the lifecycle routes create, draft and claim, start and resume. The guards open again the moment the review is accepted, and they open during the accept's own push (the removal is a platform-authored proposal, not a guarded request).
- Accept (admin) validates `interpretation` (4000 characters at most) and `rejectedNodes` (ids of the stored tree, else 400). Rejections after the Genome moved are 409 `stale-base`. It builds the ops read-only, then flips the review pending to accepted with `casImportReview` (compare-and-set on status and `genomeCommit`; a concurrent second accept, or one racing a forced re-import, is 409 `invalid-state` and creates nothing).
- Rejected nodes with no rejected ancestor become `remove` ops, preceded by ops that drop every reference a surviving node holds to a removed node, criterion or hook: an `unlink` per link and an `update` for a criterion's `refines`/`satisfies`/`sourceRefs`/`hooks`, a step's `next`, or the id lists `sections`, `purposeRefs`, `features`, `requirements` and `requirementRefs`. The amended Genome is loaded and validated first, with the System's accepted-package templates; a reference no op can drop (a template's required `$self` section, a journey starting at a removed step, a load error, a hard finding the base did not have; Evolution records excepted) is 422 `rejected-node-referenced`, and the review stays pending.
- The removal commits and approves at once. It creates a linked `genome-amendment` Evolution titled `Import review: remove <n> node(s)` and a platform-authored proposal, and calls the intents accept (B.4, ontology.md §5), which pushes and approves. `amendment.systemCommit` is the approved System commit, equal to the new head. Without rejections only the interpretation is stored.
- `warnings` on the response names each live Evolution (not promoted, rejected or withdrawn) whose acceptance criteria the removal deletes; its gate fails closed until it is withdrawn or those criteria are added back.
- A failure before the approval rejects a staged candidate, flips the review back to pending, refreshes the registry and rethrows. A failure after the approval landed keeps the review accepted and returns the committed amendment. A failed accept can leave an orphan linked Evolution and an open platform proposal.
- Every review write emits `system.import-review` (status, null on clear) and the registry refresh.

## Parts registry and realization lineage (accepted contract)

Implement an immutable versioned Parts catalog with shared and System-private scopes, authorized package publication/import, exact pinned dependency validation, and inspectable provenance. Keep composition execution local and explicit through CLI/agents; model reads never run commands. Preserve separate Genome approval, application realization, and deployment gates. The CI command allowlist is not extended by package commands.

Persist realized output independently from deployment, retaining source binding, Thing, source revision, Genome revision and build/output locator or digest. Phenome ingestion verifies these associations from stored records rather than trusting emitter IDs; old records without lineage stay explicitly unknown. An admin can register a separate deployment of an existing output with `outputId`; the stored output and passed build must match the deployment repository and commit. CI sets runtime `BUILD_ID` independently from `ARTYFACT_SOURCE_COMMIT`; preview health requires the exact passed build identity, with commit-prefix compatibility only for legacy builds. Track delivery and verification in [GRREAT](../grreat/roadmap.md).
