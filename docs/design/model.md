# Appendix A — Metamodel design (packages/model, templates, Keep in Touch encoding)

## A.1 System repo layout
A Genome is a containment tree: one `node.yaml` per directory, directory depth is layer depth, a node's children are its subdirectories, and the root `node.yaml` carries the System id, template and pins. Journeys' steps and Evolutions (`evolutions/*.yaml`) sit in the same tree. A node's `files` globs attach it to app paths (there is no repo-level source map). The spec is `docs/design/ontology.md`; templates stay in `packages/templates/<kind>/<name>@<v>/template.yaml`, and a Thing template's `sections` may be overridden by the Thing.

## A.3 Loader / validate / diff
`SystemModel` = collections projected from the Genome v2 graph (`fromGraph`) + `graph`, the composed `template` and `index` (see Shared contracts and `docs/design/ontology.md`). `loadGenome` throws `LegacyGenomeError` for a v1 revision and `ModelParseError{file, issues}` for a bad tree; template nodes come from the meta@1 templates the System and its Things pin, composed with `composeTemplates`. **Validation is not hand-coded**: `validate()` = the engine `evaluate` of the graph under the composed template, with the engine packs plus the template packs the System pins (R11's "artifacts non-empty" no longer applies: a Genome-only Thing may bind no artifact). The R-list below is the *obligation inventory* the packs must cover (R1/R2/R10/R11 → `metamodel@1`; R3/R4 → `theory@1`; R5/R6/R12 → `readiness@1`; R7/R8 → `journeys@1`; R9 → `topology.private-pairs@1` + semantic candidates; authorization inheritance → `authorization@1`):
R1 every link/parent/refines/subjects/beneficiaries/acceptanceCriteria resolves → error · R2 containment acyclic, one parent → error · R3 Purpose beneficiaries non-empty, resolve to ext person/group → error · R4 non-deferred claim has indicator + evaluationMethod → missing · R5 enabled requirement has ≥1 criterion with it in sourceRefs → missing · R6 non-deferred criterion has ≥1 hook; `binding: defined` → warning "implementation missing" · R7 in-scope screen enumerates ≥1 component; affordances have actor + effects → missing · R8 journey step refs resolve; every in-scope screen in ≥1 journey → warning · R9 topology: field/effect matching `/recipients?\[\]|recipient list|bulk/i` or `cardinality: many` on outgoing-direct → error (C.system.topology) · R10 criterion ownerId is system or existing thing; subjectId resolves → error · R11 Thing.artifacts non-empty; sections resolve → error · R12 templateRef resolves to a known id@version; required template sections/criteria present → error.
`diffModels` compares byId structurally (ignoring revision); `affectedCriteria` = subject ∈ changed∪removed or sourceRefs changed; `affectedJourneys` via journeysByNode. `overlap` = shared nodes + criteria/journeys both deltas touch.

## A.6 Parts and artifact aspects (accepted contract; implementation tracked in GRREAT)

This supersedes A.3 R11's non-empty artifact requirement: a Thing is a Genome-defined subject and may have zero Parts and zero artifacts. A System remains a distinct context/governance wrapper even when its only Thing is a full application.

A Part is an immutable versioned reusable package, partial or complete, containing optional model/files, named inputs/defaults, and pinned nested Parts. Shared Parts cannot depend on System-private Parts. A recipe names each contribution separately, selects/masks/parameterizes content, declares scoped replacements or combinations, and may run explicit authoring commands. Undeclared collisions stop composition. Loading a Genome never executes a recipe or command. Explicit local execution runs nested contributions and their recipes before containing Part adapters, then the outer recipe; repeated contributions retain separate command identity.

Composition produces ordinary saved Genome and source files plus provenance: pinned package/input identities, contribution identity, and retained/adapted/replaced/combined/excluded output mappings. Repeated uses receive distinct identities. Explicit command execution updates changed/deleted mappings and records command-created files with command identity rather than an invented package source path. Extraction copies selected/generalized content from a Thing revision without mutating it; masked content is absent from the package payload. Upgrades are explicit three-way comparisons of prior generated baseline, customized current content, and new output; preserve edits or surface conflicts. Published versions cannot mutate. Legacy templates and IDs remain supported.

Source Artifact means authored code/config/assets/manifests, excluding dependencies/caches/generated output. Realized Artifact means one specific build output with its own identity, source and Genome lineage, locator/digest, and separate deployment instances. Rebuilding identical source can produce distinct outputs. Historic output identity remains unknown where unavailable. Phenome evidence must resolve through authoritative Thing/source/output association.

See [the delivery roadmap](../grreat/roadmap.md) for implementation status and acceptance.

The self-Genome (`genome/`, `system.artyfact`) has ten Things: platform, ci, site, model, ontology, semantic, rules, templates, cli and effects. Edits start from an intent message: the engine routes and translates it into ops, `validateOps` checks them, and an accepted Proposal becomes a Genome commit through the normal candidate path (`docs/design/ontology.md`).

## A.7 UI nodes in the self-Genome

The platform describes its own UI under `genome/thing.platform/grouping.platform.ui/`. A grouping is an undrawn kind, so its screens land in the Thing's Experience band. There is one `screen.<view>` per routed view, with `route` and page `states`. Tabs, panels and signifier chip strips are `component.<screen>.<code-id>` under their screen, with the chip vocabulary as `states` ("glyph word (tone)"). Each action is an `affordance.<screen>.<verb-object>` with `actor`, `trigger`, `preconditions`, `effects` and `failure`; the endpoint it calls is named in its description, because `invokes` cannot target an endpoint in the current Thing template. The shell is a `component.shell` tree. Ids are code identities and never change on a rename; `name` and `route` do. Journey steps link to their screen with `stepScreen`, and a screen links to its feature with `serves`.
