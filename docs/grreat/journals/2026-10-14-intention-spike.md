The app has the intended building blocks, but continuity weakens at three boundaries: keeping acceptance contracts pinned safely, taking a new ontology into implementation, and showing trustworthy feedback for the thing being inspected. The following priorities are recommendations, not newly accepted product decisions.

## Confirmed mismatches

1. **P1 — Acceptance-criterion changes can escape required replanning.** A task can check `C.people.list`, then a later accepted Genome changes that criterion's claim without changing its subject. [Compatibility checking](../../../apps/platform/worker/lifecycle-service.ts#L57) only builds scope from task read/write nodes; [diff/overlap](../../../packages/model/src/diff.ts#L37) does not count a changed criterion itself as an affected criterion. An isolated execution of the real functions returned `changed: [C.people.list]`, `affectedCriteria: []`, and no overlap. [Promotion](../../../apps/platform/worker/lifecycle-service.ts#L219) uses that check and evaluates against the old pinned Genome. This can admit continuation under a changed acceptance contract despite the explicit-replan invariant. Include checks and their hook/contract dependencies in compatibility analysis; prove criterion-only changes block while genuinely disjoint changes remain allowed. This reproduces the overlap false negative, not an end-to-end successful promotion.

2. **P1 — Thing-scoped operations can target another Thing.** [Deployments](../../../apps/platform/src/views/phenome/PhenomeView.tsx#L25) filters builds/events by `thingId`, then mounts unscoped `Operations`. [Operations](../../../apps/platform/src/views/phenome/Operations.tsx#L8) loads all System bindings and defaults to the first; metric requests and flag writes use that selected binding. Opening Thing B can therefore show B's deployments beside Thing A's metrics and flag controls. The binding selector exposes the ID, but the workspace context does not constrain it. Carry Thing scope into binding selection and reset selection/editor state when scope changes. Static path verified; multi-Thing browser scenario remains to run.

3. **P2 — Start does not provide a complete first implementation handoff.** The [accepted-import instructions](../../../apps/platform/src/views/start/index.tsx#L25) show bootstrap followed by `plan create --file plan.json`, but neither generate that file nor provide the CLI's required admin-token/platform setup. The browser token does not configure the shell. [Bootstrap](../../../packages/cli/src/lifecycle.ts#L147) writes only reviewed Genome files and invokes init; if those files declare a new app binding, [init](../../../packages/cli/src/init.ts#L433) refuses when neither local app content nor a committed remote app exists. The supplied starter creates only a System; the [planner](../../../apps/platform/worker/tasks/planner.ts#L312) cannot implement nodes without a source binding. These cases require local authoring, which is intentional, but the displayed next steps do not bridge them. Give the coordinator an executable handoff for source/bootstrap preparation, credentials/origin, and plan drafting, then return to review. Do not solve this by requiring Parts or adding a hosted agent runner.

4. **P2 — Runtime evidence is not scoped consistently to the deployment being reviewed.** [Outcome criteria](../../../apps/platform/src/views/phenome/PhenomeView.tsx#L168) use [candidate/promoted-revision evaluations](../../../apps/platform/src/model/useModel.tsx#L28), not the selected deployment/output or ingested criterion events. Changing `?deployment=` therefore changes event rows without changing the criterion verdict scope. Separately, [event storage](../../../apps/platform/worker/do/phenome-store.ts#L153) filters event rows but computes version totals/metadata globally; two deployments of the same output can show combined counts and the latest metadata when inspecting only one. Preserve the distinction between an observation, its evaluation and a verdict; require explicit output/deployment provenance for an observed verdict and apply matching filters to summaries. Raw events or counts must never automatically become passes. Static paths verified; no live outcome evaluation claimed.

5. **P2 — Runtime history can disappear from a Thing view.** [The API](../../../apps/platform/worker/do/phenome-store.ts#L38) returns the newest 50 events with `nextBefore`; [the view](../../../apps/platform/src/views/phenome/PhenomeView.tsx#L29) never follows that cursor and filters by Thing/build only after fetching the System-wide page. Fifty newer events from Thing A can make Thing B say “No events ingested” despite retained evidence. Add scoped retrieval and accessible paging with truthful empty/loading/error states. Existing custom measurements already demonstrate a paged UI.

6. **P2 — Interrupted work is counted but not offered by the CLI.** [The server](../../../apps/platform/worker/do/plan-summary.ts#L13) treats expired claimed/working tasks as awaiting an agent. [The CLI's next-task helper](../../../packages/cli/src/lifecycle.ts#L60) considers only pending tasks. With only an expired task, the app signals work waiting but `plan tasks` offers no claim command. Manual resume remains available. Derive availability consistently and print a resume/reclaim action that retains credential fencing and prior work.

## Product coherence recommendation

The Review page describes itself as the inbox for decisions and can say “Nothing is waiting on you,” while [its queue deliberately excludes Task attempts](../../../apps/platform/src/views/review/queue.ts#L89). Task selection and integrated promotion live in Work, and Home correctly points those counts there. This is not a backend omission or a violation of the current Work-specific UI contract. It is a product-language/navigation mismatch: surface all pending decisions in one discoverable inbox, or explicitly qualify Review's scope and cross-link outstanding plan decisions. Home's plan attention links currently open the general Work list rather than the relevant plan.
